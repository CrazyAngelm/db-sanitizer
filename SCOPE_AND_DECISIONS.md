# Границы MVP и принятые решения

## 1. Цель MVP

Создать убедительный proof of concept, который полностью демонстрирует требования тестового задания на одной PostgreSQL-схеме и не превращается в промышленную TDM-платформу.

Результат должен выглядеть как небольшой инженерный инструмент, а не как набор SQL-скриптов и не как архитектурная презентация без работающего кода.

## 2. Обязательный сценарий

1. Пользователь задаёт исходную и целевую PostgreSQL через переменные окружения.
2. Пользователь описывает чувствительные столбцы и группы консистентности в YAML.
3. Инструмент проверяет конфигурацию и схему.
4. Инструмент потоково собирает уникальные исходные значения в виде HMAC-ключей.
5. Локальная LLM пакетно генерирует правдоподобные уникальные замены.
6. Реестр сохраняет соответствие `group + source_hmac -> replacement`.
7. Greenmask создаёт санитизированный логический дамп, вызывая внешний mapping-transformer.
8. Дамп восстанавливается в целевую БД.
9. Verifier проверяет структуру, строки, внешние ключи, уникальность, консистентность и разнообразие.
10. Формируются `report.json` и `report.md`.

## 3. Выбранный стек

| Область | Решение | Причина |
|---|---|---|
| СУБД | PostgreSQL 16 | Один поддерживаемый зрелый вариант; удобный dump/restore и introspection. |
| Data plane | Greenmask 0.2.22 | Готовый OSS-инструмент потокового логического дампа, преобразования и восстановления PostgreSQL. |
| Оркестрация | LangGraph 1.2.x | Выполняет прямое требование об агентском каркасе, поддерживает state graph и checkpointing. |
| LLM runtime | локальная Ollama | Исходные данные не должны покидать контур; есть structured output. |
| Модель по умолчанию | `qwen3:4b-instruct` | Относительно компактная многоязычная локальная модель; модель конфигурируема. |
| Язык интеграции | Python 3.12 | Быстрая интеграция с LangGraph, PostgreSQL и Ollama. |
| Доступ к PostgreSQL | psycopg 3 | Современный драйвер с server-side cursors и потоковым чтением. |
| Валидация | Pydantic 2 | Typed contracts для policy, graph state и LLM structured output. |
| Реестр | SQLite | Достаточно для одиночного job-процесса, простая переносимость и resume. |
| Запуск | Docker Compose + Makefile | Проверяемый локальный стенд одной командой. |
| Тесты | pytest | Unit и integration tests. |

Точные Python-зависимости должны быть закреплены lock-файлом в итоговом репозитории. Docker-образы должны быть закреплены точными тегами или digest.

## 4. Что входит в MVP

- только PostgreSQL;
- вход только через подключение к исходной БД;
- санитизированный логический дамп как основной выход;
- автоматическое восстановление в целевую БД для демонстрации и проверки;
- четыре типа данных: `person_name`, `email`, `phone`, `address`;
- только явно перечисленные scalar text/varchar columns;
- сквозные замены через декларативные consistency groups;
- сохранение `NULL`;
- поддержка `UNIQUE` через уникальные замены;
- PK/FK не меняются в демонстрации;
- возможность трансформировать текстовый natural key только при явном перечислении всех связанных столбцов в одной группе;
- локальная LLM, пакетные запросы, JSON Schema/Pydantic-валидация;
- Greenmask `Cmd` transformer в JSONL-режиме;
- LangGraph с персистентным checkpointing;
- CLI и `make demo`;
- автоматические отчёты и проверки;
- демонстрационная схема, синтетический seed и before/after sample;
- unit, integration и performance-smoke tests.

## 5. Что намеренно не входит

- MySQL и MSSQL;
- приём произвольного dump-файла как отдельный пользовательский режим;
- web UI, REST/gRPC API, очередь задач, RBAC, SSO;
- реальная многопользовательская платформа на 200 одновременных пользователей;
- Kubernetes, Helm, S3, облачный control plane;
- автоматическое обнаружение PII;
- обработка свободного текста, JSON/JSONB, файлов и документов;
- OCR, Presidio и NER;
- database subsetting;
- обратимое шифрование/токенизация;
- дифференциальная приватность;
- идеальное статистическое моделирование распределений;
- изменение всех типов PK/FK;
- поддержка любой PostgreSQL-схемы без настройки;
- production hardening, HA и централизованный secrets manager.

Эти исключения должны быть прямо указаны в итоговом README как ограничения тестового MVP и возможные направления развития.

## 6. Интерпретация сквозной консистентности

Одинаковая нормализованная строка должна иметь одну замену во всех столбцах одной `consistency_group`.

Пример:

```text
person_name:
  customers.full_name
  orders.billing_name
```

`Иван Петров` в обоих столбцах заменяется на одно и то же значение.

Группа является необходимой семантической границей. Одинаковый raw-текст в несовместимых типах — например имя и часть адреса — не обязан иметь одну замену, потому что это нарушило бы правдоподобность типов.

## 7. Интерпретация «команда около 200 человек»

Для тестового задания это означает:

- одна документированная команда запуска;
- конфигурация вместо правок кода;
- изолированные каталоги запусков;
- стабильные exit codes;
- idempotent/resumable job;
- структурированные логи;
- отсутствие ручных шагов в happy path;
- возможность запуска из CI/job scheduler.

Это не означает необходимость писать многопользовательский сервер.

## 8. Интерпретация «большие объёмы»

Обязательны:

- server-side cursors при предварительном сборе;
- обработка данных Greenmask потоково;
- отсутствие загрузки всех строк таблицы в память;
- отсутствие LLM-вызова на каждую строку;
- LLM-вызовы только на отсутствующие уникальные mapping keys и пакетами;
- SQLite-реестр на диске;
- performance smoke на 100 000 строк или больше.

Жёсткий throughput SLA не задаётся. В README нужно привести фактически измеренный benchmark и окружение.

## 9. Политика приватности LLM

Raw production values запрещено отправлять в модель. LLM получает только:

- тип сущности;
- локаль;
- требуемое количество;
- ограничения формата и длины;
- синтетические примеры формата при необходимости.

Модель генерирует новый пул значений независимо от исходных PII. Сопоставление выполняет детерминированный код через HMAC-ключи.

## 10. Рассмотренные альтернативы

### Полностью собственный pipeline на COPY/psycopg

Отклонён: потребовал бы больше кода для dump/restore, типов и схемы, что противоречит приоритету готовых OSS-компонентов.

### Только Greenmask built-in transformers

Отклонён как единственное решение: не демонстрирует обязательное использование LLM и сложнее обеспечить централизованную таблицу LLM-замен для всех полей.

### PostgreSQL Anonymizer

Подходит для SQL-ориентированного masking, но интеграция с LLM и внешним mapping registry потребовала бы отдельной обвязки; для этого PoC Greenmask ближе к нужному dump/restore pipeline.

### Faker без LLM

Отклонён: не выполняет прямое требование задания.

### LLM на каждую строку

Отклонён: непредсказуемо, медленно, дорого и плохо масштабируется.

### Облачный LLM

Отклонён для happy path: создаёт риск вывода чувствительных сведений за контур и усложняет проверку.

### UI/API/Kubernetes

Отклонены как не требуемые тестовым заданием и отвлекающие от корректности.
