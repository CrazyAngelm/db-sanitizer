# Требования исходного задания

Этот документ содержит только требования, извлечённые из исходного тестового задания. Проектные решения и ограничения MVP находятся в других файлах.

Исходный документ сохранён в `references/original-test-task.docx`, его текстовая выгрузка — в `references/original-test-task.txt`.

## Контекст и цель

Компания регулярно передаёт копии производственной базы за пределы production-контура: разработчикам, тестировщикам, аналитикам и подрядчикам. Чувствительные данные должны быть обезличены, но база обязана сохранять пригодность для разработки, тестирования и аналитики.

Цель — создать не одноразовый скрипт, а регулярно запускаемый инструмент санитизации одной выбранной СУБД.

## Функциональные требования

| ID | Требование |
|---|---|
| FR-01 | Поддержать одну СУБД из PostgreSQL, MySQL или MSSQL. |
| FR-02 | Принимать исходную БД как дамп или подключение и формировать санитизированную версию. |
| FR-03 | Заменять чувствительные значения правдоподобными значениями соответствующего типа. |
| FR-04 | Использовать LLM для генерации замен. |
| FR-05 | Обеспечить сквозную консистентность: одно исходное значение получает одну замену во всех соответствующих таблицах и полях. |
| FR-06 | Сохранить связи, зависимости, внешние ключи и ссылочную целостность. |
| FR-07 | Не менять количество строк. |
| FR-08 | Не сводить данные к единообразным заглушкам; сохранять вариативность и полезное разнообразие. |

## Требования к реализации

| ID | Требование |
|---|---|
| IR-01 | Максимально использовать существующие open-source-компоненты. |
| IR-02 | Писать собственный код преимущественно для интеграции и недостающей логики, не переизобретать готовое. |
| IR-03 | Использовать существующий агентский фреймворк для оркестрации LLM-агентов. |
| IR-04 | Не создавать собственный агентский каркас с нуля. |

## Масштабируемость и расширяемость

| ID | Требование |
|---|---|
| NFR-01 | Решение рассчитано на регулярную эксплуатацию командой порядка 200 человек. |
| NFR-02 | Запуски должны быть воспроизводимыми, автоматизируемыми, предсказуемыми и надёжными. |
| NFR-03 | Большие объёмы должны обрабатываться без существенной деградации: потоково или пакетно, с эффективным использованием памяти. |
| NFR-04 | Архитектура должна допускать расширение на другие документы и форматы без переписывания ядра. |
| NFR-05 | Нужны модульность, слабая связанность и разделение механики обработки от правил замены. |
| NFR-06 | Требуется обосновать архитектуру, масштабируемость, расширяемость, альтернативы и компромиссы. |

## Запуск и сдача

| ID | Требование |
|---|---|
| RR-01 | Решение должно быть воспроизводимо и реально запускаться. |
| RR-02 | При сдаче репозиторием нужна понятная инструкция запуска. |
| RR-03 | Формат решения выбирает кандидат: контейнеризированная утилита, сервис, job-процессор и т. п. |
| DEL-01 | Сдать репозиторий с исходным кодом и инструкцией либо развёрнутый стенд. |
| DEL-02 | Приложить README с обоснованием формата, перечнем OSS-компонентов и доработок, механикой замен, способом использования LLM, архитектурой и масштабируемостью. |
| DEL-03 | Желательно показать «до/после», подтверждающее обезличивание при сохранении связей, объёма и разнообразия. |

## Что исходное задание не определяет

Источник не задаёт:

- конкретную СУБД из трёх;
- обязательную поддержку и дампа, и подключения одновременно;
- перечень чувствительных типов и способ их обнаружения;
- допустимый LLM-провайдер и конкретную модель;
- формат конфигурации;
- точный объём демонстрационных данных и SLA;
- требование обратимости замен;
- требование одинакового результата между независимыми запусками;
- точную метрику «сохранения распределения»;
- обязательный UI, API, Kubernetes или многопользовательский сервер.

Эти пробелы закрыты явными решениями в `SCOPE_AND_DECISIONS.md`.
